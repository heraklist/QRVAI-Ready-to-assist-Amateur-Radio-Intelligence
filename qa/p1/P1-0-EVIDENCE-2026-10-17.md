## Source architecture, security and policy boundaries

- Task 1 has no independent shadow taxonomy: parses the owner's `docs/architecture/skill-and-subskill-registry-v0.5.md` and `capability-register-v0.5.md`, rejecting missing or swapped ID/owner context. Original Domain names and planned references remain canonical.
- Task 2's only test Skills are in disposable Python `TemporaryDirectory` fixtures; no `staging/p1-domain-skills/skills/*` live source has been created. The empty stage is valid **only** for P1.0 (approved zero required IDs), whereas a missing required Domain is rejected.
- Task 3 only statically validates expectations; **it does not execute LLM/host routing**, does not certify a country's license privileges and does not send emergency traffic or operate equipment. Fail-closed guardrail expectations cover Greece-first legal uncertainty, simulated EmComm, CAT/PTT/TX, privacy and fake provider data.
- Task 4 creates a **separate review-only** ZIP in temporary tests; ZIP metadata must pass before payload reading; the tool must not extract to a filesystem, contain credentials/manifest, or be presented as a Plugin Creator upload.
- Task 5's dedicated read-only `.github/workflows/p1-domain-skills-ci.yml` has PR path filtering and pinned GitHub actions; both P1 and V0 test suites run in one job, so a P1-only change checks untouched V0. Its archive hash equality is a development-baseline regression guard, not a claim of official packaging readiness.
- **No changes authorized/performed:** `main` merge, existing PR closure, production deployment, Vercel credentials/issuer, Plugin Creator create/update/install, external providers, CAT/PTT/TX, physical station/SDR bridge, private logbook access or marketplace listing.

## Rulings, limitations and handoff

**Ruling 1 — Real Actions instead of local worktree:** the current Chat environment has GitHub connector write access but no authenticated local repository checkout; observed RED/GREEN runs are genuine Actions runs on precise GitHub commits. **Risk if wrong:** non-Linux development environment portability remains untested. Local filesystem command execution: **NOT_EXECUTED**.

**Ruling 2 — Parser blank-value issue:** initial regex `\s*` could consume newlines and mistakenly accept a missing context from the next Markdown field; the test caught it, and using horizontal whitespace only made the test pass. **Risk if wrong:** future registry Markdown layout changes may need a versioned parser/test change, not silent re-interpretation.

**Ruling 3 — CI bring-up:** an initial workflow was introduced alongside the first failing test to make branch-scoped RED visible via real Actions; tests for the final CI metrics and hash contract were then added before the missing workflow behavior. **Risk if wrong:** this setup is CI infrastructure not a feature-level production RED defect.

**Ruling 4 — V0 archive fingerprint:** P1.0 pins the pre-existing deterministic 12-file archive SHA rather than weakening the V0 packaging scope. **Risk if wrong:** an independently approved V0 source change will require a separately reviewed, explicit baseline/hash update; P1.0 alone must not silently change it.

**Ruling 5 — No deployable P1 package at Stage 0:** the ZIP builder's own negative test rejects an empty approved owner list; it can only create fixture output during P1.0. **Risk if wrong:** an empty P1 ZIP cannot be previewed, which is intentional to avoid an installable but empty product claim.

**Ruling 6 — Author review cannot replace independent review:** source correctness and same-SHA CI cover this Draft work, but an independent human/security reviewer and actual installed host E2E remain `NOT_EXECUTED`.

**P1.0 completion semantics:** only after the final ledger-commit P1 CI passes and the PR diff confirms only P1 scripts/tests/QA/workflow changes may the owner label this **P1.0 SOURCE TEST FOUNDATION VERIFIED IN DRAFT**. This does **not** approve P1.1 implementation, any deployment or plugin installation. P1.1 RF pilot (B07/B08) needs a separately written and reviewed TDD plan.
